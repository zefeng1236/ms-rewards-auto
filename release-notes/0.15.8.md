# 0.15.8：修复容器里「加了 GPU 参数却没权限」导致的 WebGL 不可用

修 0.15.7 引入的一个**容器部署回归**（只影响 Docker，桌面版行为与 0.15.7 相同）：
映射了 GPU 的宿主升级后 **WebGL 会变成不可用**——比升级前（SwiftShader 软件渲染）更糟。

---

## 一、问题

0.15.7 让容器在探测到 `/dev/dri` 时自动追加 `--use-gl=angle,--use-angle=vulkan`。
但容器内 `/dev/dri/renderD128` 的属组是**宿主的 GID**（我这边 NAS 是 `root:105`），
容器里既没有这个组名、运行时的 `node` 用户也不在其中 —— 于是打不开渲染设备，
ANGLE 只能挑到 **lavapipe**（软件 Vulkan），而这条路让 WebGL **直接返回 null**：

```
ANGLE (Mesa, Vulkan 1.3.230 (llvmpipe (LLVM 15.0.6 256 bits)), llvmpipe)
opengl: unavailable_off · webgl: null
```

同一套参数**以 root 跑却完全正常**（`ANGLE (AMD, … (RADV RENOIR), radv)`、`opengl: enabled_on`）
——这也是 0.15.7 没测出来的原因：当时的手工验证用的是 root，而真实运行身份是 `node`。

## 二、修法

`entrypoint.sh` 启动时：

1. 按设备真实 GID 建组（如 `dri105`）并把 `node` 加进去（容器重建会重置 `/etc/group`，所以每次启动都做，幂等）；
2. 用 `gosu node test -r <设备>` **实测能不能读**；
3. 能读才追加 `--use-gl=angle,--use-angle=vulkan`；**读不到就不加参数**（保持 SwiftShader，至少 WebGL 还在）。

日志会明确打印走哪条路：

```
[entrypoint] /dev/dri/renderD128 可访问（组 dri105 / gid 105）
[entrypoint] 检测到可访问的 /dev/dri → 启用 ANGLE-Vulkan 硬件渲染
```

实测（NAS，**以运行时的 node 身份**）：

| 条件 | WebGL 渲染器 | GPU 状态 |
|---|---|---|
| 修好后（自动追加参数） | `ANGLE (AMD, Vulkan 1.3.230 (AMD Radeon Graphics (RADV RENOIR)), radv)`，maxTex 16384 | `opengl: enabled_on`、`gpu_compositing: enabled` |
| 不带参数（对照） | `ANGLE (Google, … SwiftShader Device (Subzero))` | `opengl: disabled_off`，但 **WebGL 可用** |

## 三、顺带修的：`docker restart` 后图形会话起不来

`restart: unless-stopped` 的崩溃自动重启、或手动 `docker restart`，都不会清 `/tmp`。
残留的 `/tmp/.X1-lock` 会让新的 Xvnc 直接退出（日志 `A VNC server is already running as :1`），
表现为容器起来了、但「去登录」打不开图形会话。新版启动前先判断没有活着的 Xvnc，再清锁。

## 升级说明

桌面版直接覆盖安装，配置与账户数据不受影响（本版对桌面无行为变更）。

Docker 部署**建议升级**（尤其映射了 `/dev/dri` 的）：

```bash
docker compose pull && docker compose up -d
```

升级后如果想确认硬件 GL 有没有生效，看容器的这两行日志即可：

```bash
docker logs ms-rewards 2>&1 | grep entrypoint
```
